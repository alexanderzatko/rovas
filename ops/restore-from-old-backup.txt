Restoring from a database backup made before the module reorganization
======================================================================

Background
----------
In the current codebase, Drupal contrib and custom modules live under:

  sites/all/modules/contrib/<name>/
  sites/all/modules/custom/<name>/

Older database backups (made before this reorganization) store file paths
in the flat layout:

  sites/all/modules/<name>/

If you restore such a backup while the filesystem already has the new
structure, Drupal will be unable to find its modules and the site/drush
will fail to bootstrap. Follow the steps below to reconcile the database
with the filesystem.


Step 1 — Restore the backup
----------------------------
Restore the database normally (e.g. via backup_migrate, drush sql-cli,
or phpMyAdmin). Do not start using the site yet.


Step 2 — Fix module paths in the system table
----------------------------------------------
The system table tracks every module's file path. Run:

  ssh root@magura
  cd /var/www/rovas
  php ops/fix_system_paths.php

This script updates all old flat paths to their correct contrib/ or
custom/ equivalents by checking what exists on disk. It prints each
path it updates, and warns about any modules it cannot find.


Step 3 — Rebuild the class registry
-------------------------------------
The registry table maps PHP class and interface names to the files that
define them. After a path change it must be rebuilt from scratch:

  php ops/rebuild_registry.php

This scans all PHP files under includes/, modules/, and
sites/all/modules/ and repopulates the registry and registry_file tables.
It handles both legacy unnamespaced classes and PSR-4 namespaced ones
(e.g. Drupal\service_container\...).


Step 4 — Fix the Composer autoloader paths
-------------------------------------------
4a. Fix the composer_manager_vendor_dir variable
-------------------------------------------------
The backup restores the variable table, which may contain an old vendor
directory path. composer_manager uses this variable to locate autoload.php;
if it points at the wrong place the site will throw a RuntimeException on
every page load even after caches are cleared.

Check and fix it:

  mysql -u rovas -p rovas -e "SELECT name, value FROM variable WHERE name = 'composer_manager_vendor_dir';"

The correct value is sites/all/vendor (14 characters). If it is wrong, fix it:

  mysql -u rovas -p rovas -e "UPDATE variable SET value = 's:16:\"sites/all/vendor\";' WHERE name = 'composer_manager_vendor_dir';"

4b. Fix autoloader file references
------------------------------------
The vendor autoloader at sites/all/vendor/ may still reference old module
paths. Check and fix these files if needed:

  sites/default/files/composer/composer.json
  sites/all/vendor/composer/autoload_static.php
  sites/all/vendor/composer/autoload_namespaces.php
  sites/all/vendor/composer/autoload_psr4.php

Search for any occurrence of "all/modules/<name>/" (without contrib/ or
custom/) and replace with "all/modules/contrib/<name>/" (or custom/ as
appropriate). Example one-liner for service_container:

  sed -i 's|all/modules/service_container/|all/modules/contrib/service_container/|g' \
    sites/default/files/composer/composer.json \
    sites/all/vendor/composer/autoload_static.php \
    sites/all/vendor/composer/autoload_namespaces.php \
    sites/all/vendor/composer/autoload_psr4.php

NOTE: As of the last deploy these files are already correct on Magura.
Step 4b is only necessary if the backup also overwrote those files,
or if composer-manager regenerated them from the restored variable data.


Step 5 — Clear the bootstrap cache via MySQL
---------------------------------------------
The cache_bootstrap table holds serialized module paths that were cached
before the backup was made. If those paths still use the old flat layout,
Drupal will crash trying to include missing files during bootstrap — before
drush can even run the cache-clear command.

Wipe all cache tables directly via MySQL first:

  mysql -u rovas -p rovas -e '
    TRUNCATE cache;
    TRUNCATE cache_bootstrap;
    TRUNCATE cache_block;
    TRUNCATE cache_field;
    TRUNCATE cache_filter;
    TRUNCATE cache_form;
    TRUNCATE cache_menu;
    TRUNCATE cache_page;
    TRUNCATE cache_path;
    TRUNCATE cache_rules;
    TRUNCATE cache_token;
    TRUNCATE cache_update;
    TRUNCATE cache_variable;
    TRUNCATE cache_views;
    TRUNCATE cache_views_data;
  '

Replace the -p password as needed (check sites/default/settings.php).


Step 6 — Clear caches and run database updates
-----------------------------------------------
  cd /var/www/rovas
  drush74 cc all -y
  drush74 updb -y


Quick reference (all steps on Magura)
--------------------------------------
  ssh root@magura
  cd /var/www/rovas
  php ops/fix_system_paths.php
  php ops/rebuild_registry.php
  mysql -u rovas -pPASSWORD rovas -e "UPDATE variable SET value = 's:16:\"sites/all/vendor\";' WHERE name = 'composer_manager_vendor_dir';"
  mysql -u rovas -pPASSWORD rovas -e 'TRUNCATE cache; TRUNCATE cache_bootstrap; TRUNCATE cache_block; TRUNCATE cache_field; TRUNCATE cache_filter; TRUNCATE cache_form; TRUNCATE cache_menu; TRUNCATE cache_page; TRUNCATE cache_path; TRUNCATE cache_rules; TRUNCATE cache_token; TRUNCATE cache_update; TRUNCATE cache_variable; TRUNCATE cache_views; TRUNCATE cache_views_data;'
